===========================

test_get_transfer_invalid_id_integer_not_found_404
Verwacht: 404
Voorspeld (nu): 200 (+ null body)
Klopt: NEE
Reden: get_transfer() retourneert None bij een onbekend ID (zoals 9999999). De GET-handler in de code controleert dit resultaat niet en stuurt standaard een 200 OK terug.

test_get_transfer_invalid_id_string_404
Verwacht: 404
Voorspeld (nu): 500
Klopt: NEE
Reden: Bij het opvragen van het ID "AAAAAAAAAAA" probeert de server dit via int(paths[1]) om te zetten naar een integer. Dit veroorzaakt een ValueError die niet wordt afgevangen, wat resulteert in een servercrash (500).

test_get_transfer_invalid_id_string_integer_non_alphanumeric_not_found_404
Verwacht: 404
Voorspeld (nu): 500
Klopt: NEE
Reden: Zelfde probleem als hierboven; de ValueError bij het omzetten van "ABC6d1Xyz$" naar een integer levert een 500 op.

test_post_and_get_transfer_201
Verwacht: transfer_status = "Pending"
Voorspeld (nu): "Scheduled"
Klopt: NEE
Reden: Bij het aanmaken (POST) van een transfer wordt de meegestuurde transfer_status "Pending" in de backend blijkbaar overschreven of genegeerd (vermoedelijk hardcoded op "Scheduled" in de datalaag of router). Hierdoor falen latere asserts op de GET-response.

test_delete_transfers_collection_not_allowed_405
Verwacht: 405
Voorspeld (nu): 403
Klopt: NEE
Reden: Een DELETE verzoek op de volledige /transfers collectie wordt afgevangen door de Role-Based Access Control (RBAC). De gebruikte API key heeft helemaal geen DELETE-rechten, waardoor de server direct een 403 Forbidden geeft, nog voordat het de methode-validatie (405) bereikt.


===========================
SAMENVATTING - TESTS DIE FALEN
===========================

1. test_get_..._invalid_id_integer_not_found_404 -> krijgt 200 i.p.v. 404
2. test_get_..._invalid_id_string_404 -> krijgt 500 i.p.v. 400 of 404
3. test_delete_and_get_warehouse_404 -> krijgt 200 i.p.v. 404 (bij de laatste GET)
4. test_delete_..._collection_not_allowed_405 -> krijgt 500 (bij warehouses/locations) of 403 (bij transfers) i.p.v. 405
5. test_post_..._incomplete_400 -> krijgt 500 i.p.v. 400
6. test_post_and_get_transfer_201 -> assert faalt (krijgt 'Scheduled' i.p.v. 'Pending')

Onderliggende oorzaken (4x):

* Geen None-check bij GET: De GET-by-id handlers checken niet of het resultaat `None` is voordat ze status 200 + de (lege) body terugsturen. Dit veroorzaakt zowel de standaard 404-fouten als de fout bij het opvragen van een zojuist verwijderd object.
* Geen Error Handling op paden: De URL path parsing bevat geen `try-except` voor `ValueError` exceptions. Het direct parsen van strings naar integers (`int(paths[1])`) crasht de server met een 500.
* Geen validatie op padlengte: Handlers checken de padlengte (`len(paths)`) niet goed bij collectie-mutaties. Hierdoor levert `int(paths[1])` een `IndexError` op (500), tenzij de RBAC-rechten (zoals bij transfers) de call al eerder afkappen met een 403.
* Overschrijven van geldige payload-data: Bij het aanmaken van transfers overschrijft of negeert de datalaag of router legitieme input-data (zoals `transfer_status`) en forceert een hardcoded default waarde.
